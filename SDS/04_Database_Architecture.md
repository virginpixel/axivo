# Axivo Software Design Specification

# Document 04 - Database Architecture

## Chapter 1 - Database Philosophy

### Purpose

This document defines the database architecture, design principles, naming standards and relational model for Axivo.

---

### Database Engine

Primary database:
- PostgreSQL

ORM:
- Prisma ORM

---

### Design Principles

- Normalize data where practical
- Avoid duplicated business data
- Enforce referential integrity
- Use UUID primary keys
- Store UTC timestamps
- Soft delete operational records where applicable
- Immutable audit records

---

### Central Entity

The People table is the central business entity.

Major modules reference People rather than storing duplicate employee information.

Examples:
- Requests
- Assets
- Applications
- Licenses
- Credentials
- Documents

---

### Multi-Company Model

Business records belong to a company unless explicitly global.

Global entities include:
- System Roles
- Approval Role definitions
- Asset template definitions
- System configuration

Company-scoped entities include:
- People
- Departments
- Forms
- Applications
- Assets
- Contracts

---

### Database Standards

- snake_case table names
- snake_case column names
- Foreign keys for all relationships
- Indexed lookup columns
- No business logic in database triggers

End of Chapter 1.

## Chapter 2 - Naming Conventions & Common Columns

### Table Naming

Rules:
- snake_case
- Singular nouns
- Descriptive names
- No abbreviations unless industry standard

Examples:
- people
- companies
- departments
- applications
- assets
- contracts

---

### Primary Keys

Every business table uses:
- id (UUID)

UUIDs are generated by the application.

---

### Standard Columns

Where applicable:

- id
- company_id
- created_at
- created_by
- updated_at
- updated_by
- deleted_at
- deleted_by
- is_active

Audit tables use immutable timestamps.

---

### Foreign Keys

All relationships use foreign keys.

Naming:

- person_id
- company_id
- department_id
- workflow_id

---

### Indexing Standards

Index:
- Foreign keys
- Employee IDs
- Email
- Asset Tags
- Status
- Lookup columns
- Frequently filtered dates

---

### Timestamp Rules

Store all timestamps in UTC.

Timezone conversion occurs only in the application layer.

End of Chapter 2.

## Chapter 3 - Core Entity Relationships

### Core Business Entities

The primary entities are:

- companies
- departments
- locations
- people
- system_users
- approval_roles
- approval_role_assignments

These entities form the organizational foundation.

---

### People Relationships

A Person may have:

- Many application assignments
- Many license assignments
- Many asset assignments
- Many requests
- Many generated documents
- Many credential deliveries

A Person belongs to:
- One company
- One department
- One position

---

### Organizational Relationships

Company
→ Departments
→ Locations
→ Forms
→ Applications
→ Assets
→ Contracts

Department
→ Department Heads
→ People

---

### Workflow Relationships

Form
→ Workflow
→ Workflow Steps
→ Approval Roles

Approval Role Assignment
→ Company
→ Approval Role
→ System User

---

### Design Rules

- No circular foreign keys
- Junction tables for many-to-many relationships
- Business history preserved
- Cascade deletes avoided for operational data

End of Chapter 3.

## Chapter 9 - Database Integrity & Constraints

### Primary Keys

All business tables use UUID primary keys generated by the application.

---

### Foreign Keys

Every relationship shall be enforced using foreign key constraints.

Cascade deletes are prohibited for operational business records.

---

### Unique Constraints

Examples:

- Company Code
- Username
- Employee ID within Company
- Asset Tag within Company
- Application Name within Company
- Department Name within Company
- Location Name within Company

---

### Check Constraints

Where applicable:

- Valid status values
- Positive quantities
- Valid date ranges
- End date greater than start date
- Subscription dates required for subscription licenses

---

### Soft Deletes

Operational records use soft delete where appropriate.

Deleted records:
- remain referenced
- remain searchable for audit (permission permitting)
- are excluded from normal queries

---

### Data Integrity Principles

- Prevent orphaned records.
- Preserve historical relationships.
- Never overwrite historical business transactions.
- Reject invalid foreign key references.

---

### Acceptance Criteria

- Referential integrity enforced.
- Invalid relationships rejected.
- Historical records preserved.
- Database remains internally consistent.

End of Chapter 9.

## Chapter 10 - Performance, Indexing & Optimization

### Performance Objectives

The database shall support fast transactional operations while maintaining data integrity.

---

### Indexing Strategy

Create indexes for:

- Primary keys
- Foreign keys
- Employee ID
- Email
- Username
- Asset Tag
- Contract expiry date
- Request status
- Workflow status
- Created date

Composite indexes shall be added for common reporting and filtering queries.

---

### Query Principles

- Use pagination for large datasets.
- Avoid SELECT *.
- Use eager loading only where appropriate.
- Prevent N+1 query patterns.

---

### Reporting

Heavy reports shall:
- Execute asynchronously where appropriate.
- Use optimized queries.
- Support future materialized views if required.

---

### Archiving

Historical data remains online.

Future versions may introduce configurable archive partitions without changing application logic.

---

### Acceptance Criteria

- Common searches remain responsive.
- Large datasets remain pageable.
- Reporting queries do not impact transactional performance.

End of Chapter 10.

## Chapter 11 - Transactions & Concurrency

### Transaction Principles

Business operations that modify multiple related records shall execute within a single database transaction.

---

### Atomic Operations

The following shall be atomic:

- Request submission
- Workflow approvals
- Asset assignment
- Credential delivery preparation
- License assignment
- Contract renewal
- Backup metadata updates

---

### Concurrency Control

The application shall prevent conflicting updates by using optimistic concurrency where appropriate.

Users attempting to save stale data shall receive a clear message to refresh before retrying.

---

### Idempotency

Repeat submissions caused by retries or network interruptions shall not create duplicate business records.

---

### Background Workers

Workers shall use transactional updates when completing queued jobs to prevent partial processing.

---

### Acceptance Criteria

- No partial business transactions.
- Duplicate submissions prevented.
- Concurrent updates handled safely.
- Database consistency maintained during failures.

End of Chapter 11.

## Chapter 12 - Backup, Recovery & Data Retention

### Backup Scope

Backups shall include:
- PostgreSQL database
- Uploaded documents
- Branding assets
- Templates
- Configuration

Excluded:
- Cache
- Temporary credential secrets
- Runtime logs

---

### Recovery

Recovery shall restore:
- Schema
- Business data
- Audit history
- Documents
- Configuration

Only System Administrators may initiate restores.

---

### Data Retention

Operational records remain until archived according to organizational policy.

Audit records are immutable.

Generated PDFs remain linked to their originating records.

---

### Purging

Automatic purging applies only to:
- Expired credential secrets
- Expired tokens
- Temporary files
- Background job history (configurable)

Business records are never automatically deleted.

---

### Acceptance Criteria

- Backup integrity verified.
- Restore completes successfully.
- Historical data preserved.
- Audit history remains intact.

End of Chapter 12.

## Chapter 13 - Security & Encryption

### Encryption

Sensitive data shall be encrypted before storage.

Encrypted values include:
- SMTP passwords
- API secrets
- Temporary credential secrets
- Encryption keys (external storage reference only)

---

### Password Storage

System User passwords are never stored in plain text.

Requirements:
- Argon2id hashing
- Unique salt
- Secure verification
- No password recovery

---

### Secret Lifecycle

Temporary credential secrets:
- Encrypted
- Delivered once
- Automatically removed after expiry
- Never permanently stored

---

### Database Access

Only the application and background worker may access PostgreSQL.

Direct client access is prohibited.

---

### Audit Protection

Audit records are append-only.

Updates and deletions are prohibited.

---

### Acceptance Criteria

- Secrets encrypted.
- Passwords hashed.
- Audit integrity preserved.
- Database inaccessible from public clients.

End of Chapter 13.

## Chapter 14 - Database Maintenance & Migration

### Schema Migrations

All schema changes shall be managed through Prisma migrations.

Requirements:
- Version controlled
- Repeatable
- Tested before production
- Rollback strategy documented

---

### Migration Principles

- Never modify production tables manually.
- Preserve existing data during upgrades.
- Back up the database before applying migrations.

---

### Maintenance

Routine maintenance includes:
- Index optimization
- Statistics updates
- Database health checks
- Backup verification
- Storage monitoring

---

### Compatibility

Database changes must remain compatible with existing application versions during controlled upgrade procedures where practical.

---

### Acceptance Criteria

- Migrations execute successfully.
- Existing data preserved.
- Rollback procedure documented.
- Maintenance tasks completed without data loss.

End of Chapter 14.

### Validation Objectives

The database design shall be verified for correctness, integrity, performance and scalability before production deployment.

---

### Functional Validation

- Foreign key integrity
- Unique constraints
- Soft delete behavior
- Workflow relationships
- Approval role assignments
- Historical record preservation

---

### Performance Validation

Test:

- Large People datasets
- Asset searches
- Request history
- Contract expiry reports
- Dashboard queries
- Concurrent users

---

### Security Validation

Verify:

- Database inaccessible from public network
- Encrypted secret storage
- Password hashing
- Audit immutability
- Permission enforcement

---

### Backup Validation

Regularly test:
- Backup creation
- Restore process
- Data integrity after restore
- Document recovery

---

### Acceptance Criteria

The database architecture is accepted when:

- Referential integrity is maintained.
- Performance targets are met.
- Security requirements pass.
- Backup and restore succeed.
- Historical data remains intact.
